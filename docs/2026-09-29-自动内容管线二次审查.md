## R1 · P1：已判为过期的审核结果仍然进入改稿并落库

**位置**：[server/api.mjs](../server/api.mjs)，第 165–181 行；[server/db.mjs](../server/db.mjs)，`saveRewrite`（第 1249 行起）。

保存审核结论时，代码正确检查 `res.saved === false` 并跳过。但后面的 `fixQs` 仍从原始 `results` 中选出所有 verdict=fix 的题，没有排除刚刚被跳过的结果。

此外，改稿模型返回后，`saveRewrite` 没有再次核对请求对应的内容版本、审核状态或期间发生的人工操作。

### 复现结果

在独立库中模拟审核期间出现一个更新的 human/ok 结论，审核替身返回 fix：

```text
模型调用顺序：review → generate
reviewed = 0
skipped = 1
rewritten = 1
最终审核：human/ok
最终 rewrite.explain：A stale rewrite should not be applied.
```

人工结论虽然保住了，题目内容仍被已经作废的审核意见改写。若用户在改稿请求进行期间操作，也没有对应的提交保护。

### 建议与验收

- 只有本轮成功保存、且仍有效的 fix 结论才能进入改稿。
- 改稿落库时再比较账户、题目、内容修订和审核修订；不能只依赖请求开始时的检查。
- 验收：审核被 skipped 后不调用 generate；改稿期间有新操作时，旧改稿不能覆盖新内容。

## R2 · P1：版本与原始题面比较，重复保存会升版，撤回改稿却不升版

**位置**：[server/db.mjs](../server/db.mjs)，第 1265–1271 行。

`promptChanged` 和 `optionsChanged` 比较的是 `questions` 基准题面，而不是该账户当前的有效题面。移除对全局镜像的改写后，这个差别尤其关键。

### 复现结果

原始选项是 `[yes, no]`、版本 1：

| 操作 | 实际版本 | 应有行为 |
| --- | --- | --- |
| 改为 `[yes, never]` | 2 | 内容改变，升版合理。 |
| 再次保存相同的 `[yes, never]` | 3 | 内容未变，不应升版。 |
| 改回 `[yes, no]` | 仍为 3 | 有效内容改变，应再升版。 |

这会同时造成两种后果：同稿重试无端作废证据；撤回选项修改时，不同题面却共用版本，旧证据无法被正确排除。

### 建议与验收

- 先计算旧有效内容 `base + previousRewrite`，再与 `base + mergedRewrite` 比较。
- 实质内容不变时保持版本；从改稿回到基准同样算内容变化。
- 明确基准内容版本升级后的组合规则，避免账户覆盖层反而把新基准版本压回去。
- 验收：首次修改、重复保存、修改回原值、仅解析变化分别有独立用例；至少包含重复保存和撤回后的证据过滤检查。

## R3 · P1：切换账户会把前一账户的审核标记带入新账户

**位置**：[src/store/useDbSync.ts](../src/store/useDbSync.ts)，第 30 行 `mergeReviewMarks`、第 224–228 行 `adopt`、第 518–534 行 `switchTo`；异步回写见第 250 行与第 290–322 行。

`switchTo(B)` 在设置新账户后调用 `adopt(pull)`，但 `adopt` 中的 `gm()` 仍是 A 的当前标记。合并函数会保留远端没有、且带 source 的所有本地标记，连 `source=ai` 的缓存结论也会保留。

这条规则可用于处理同一账户的离线操作，不能直接用于跨账户切换。

### 验证结果

直接执行现有合并函数：

```text
B 的远端标记：{}
当前 A 的本地标记：{ "a-only": { "verdict": "kill", "source": "ai" } }
合并结果：仍含 a-only 的 ai/kill
```

结合 `switchTo → adopt` 路径，这些标记会立即影响 B 的题池。当前基线被设为 B 的 remote，因此后续同步还可能把 A 的标记作为 B 的新增结论写回。

另外，A 的流水线请求返回时没有检查当前账户是否仍为 A，会把结果并入此刻的 `gm()`；`runAudit` 也缺少请求账户一致性检查。仅修同步合并函数还不足以封住切换中的异步回写。

### 建议与验收

- 区分“同账户启动合并”和“切账户接管”；切换时只接管目标账户的标记。
- 如需保留离线操作，按 accountId 保存待同步操作与缓存。
- 异步回写前检查 accountId 或会话代次；后台任务状态也按账户保存。
- 验收：A 有 kill、B 为空时切换后 B 不受影响；A 请求延迟返回时不能修改 B 的 marks、enrichments 或同步基线。
- 本项为扩大复核范围后发现的残留问题，不断言它全部由本轮提交新引入。

## R4 · P2：补逐项纠正仍读原始题面，忽略账户改写

**位置**：[server/db.mjs](../server/db.mjs)，第 954 行、第 1018–1030 行；[server/api.mjs](../server/api.mjs)，`enrich-causes` 路由。

复审已经接入 `accountRewriteMap`，但 `audit` 的 rows 仍直接来自全局 questions。缺口判断及返回的 `missingCauseAll` 因此仍是基准选项。补纠正路由直接拿这份列表交给模型。

### 复现结果

```text
基准选项：[yes, no]
旧纠正：只解释 no
A 改稿后的有效选项：[yes, never]
A 复审看到：[yes, never]
B 复审看到：[yes, no]
audit(A).missingCause.count：0
```

学生已经看到 never，但系统只保存了 no 的纠正，并认为没有缺口。如果原先未补完，模型还会继续为旧选项生成纠正。

### 建议与验收

- 审核、改稿、自检、纠正生成统一读取同一个账户有效题目视图。
- 纠正与内容版本或稳定选项身份关联，避免按旧文本继续补题。
- 验收：改换错误选项后，新选项重新进入缺口；补纠正模型实际收到的也是新选项。

## R5 · P2：自带部分纠正和缺失标签仍会被当成完成

**位置**：[src/content/bank.ts](../src/content/bank.ts)，第 35–36 行；[server/db.mjs](../server/db.mjs)，第 1018–1029 行。

`hasOwnCause` 只要发现任意一条 optionFeedback 就返回 true；服务端遇到 has_cause 就整题跳过。新增的逐项检查因而仅覆盖“没有自带纠正”的题。

此外，完成判断只检查 optionFixes 的键，不检查 optionTags。缺标签的题不会再次自动补齐，后续错因定向补练也拿不到对应标签。

### 复现结果

- 错误选项 b/c/d 只补了 b/c；目录设置 hasCause=true 后，missingCause 变为 0，d 仍无纠正。
- 一道只有一个错误选项 no 的题，保存 no 的纠正但不保存任何标签，missingCause 同样为 0。

### 建议与验收

- 目录传递逐项覆盖信息，或由服务端保留完整原生纠正，避免只用一个布尔值代表完成度。
- 合并原生纠正与账户补充后，分别统计反馈缺口和标签缺口。
- 验收：原生只覆盖一个选项、仅缺标签、改写后旧反馈失配，都能自动继续补缺。

## R6 · P2：新增“无进展”判断把部分补全误当停滞

**位置**：[src/store/useDbSync.ts](../src/store/useDbSync.ts)，第 363–365 行。

`remaining` 是仍不完整的题目数，不是仍缺少的选项数。第二批补好了同一道题的更多选项，但尚未整题完成时，题目数不会下降，`er.remaining >= lastRemaining` 就会提前停止。

### 复现结果

```text
题目有三个错误选项 b/c/d
第一批补 b：remaining = 1
第二批补 c：remaining = 1
已补选项由 [b] 增长为 [b, c]
当前 noProgress 条件：true
```

系统已经在推进，却不会继续补 d。当前自动触发标记也没有在结束后重新开启，剩余缺口需要后续会话才能再尝试。

### 建议与验收

- 服务端返回新增有效纠正数、缺失反馈数及缺失标签数。
- 以实际新增覆盖或内容变化判断进展；重复返回已有内容才算没有推进。
- 验收：连续三个批次分别补 b、c、d，应能完成；连续返回同一个 b，应停止或进入冷却。

## R7 · P2：前 60 道反复改不过，会阻塞后面的未审题

**位置**：[server/db.mjs](../server/db.mjs)，第 1207–1213 行；[src/store/useDbSync.ts](../src/store/useDbSync.ts)，第 295 行、第 337–341 行。

首次报告中的队列问题仍在。查询按 skill/id 固定排序，fix 一直留在队首；客户端把 reviewed/rewritten 非零当作进展，并在六轮后结束。

### 实际流水线路由复现

独立库中放入 61 道题。模型替身稳定返回 fix，并返回可被接受的同一份解析。调用真实 `ai-pipeline` 路由六次：

```text
第 1 轮：reviewed=60, rewritten=60, pending=61
第 2 轮：reviewed=60, rewritten=60, pending=61
第 3 轮：reviewed=60, rewritten=60, pending=61
第 4 轮：reviewed=60, rewritten=60, pending=61
第 5 轮：reviewed=60, rewritten=60, pending=61
第 6 轮：reviewed=60, rewritten=60, pending=61
最终独立受审题目数：60
第 61 道题是否被审过：false
```

这不是要求系统无限重试，而是要求单题失败不能持续占据全部处理机会。

### 建议与验收

- 首次审核优先，失败题有重试预算、冷却和下次处理时间。
- 无内容变化的改稿不要算 rewritten 进展；锁等待不消耗处理轮次。
- 维护状态按账户持久化，避免只能通过新会话推进。
- 验收：前 60 道持续失败时，第 61 道仍可获得处理；重复失败不会无上限增加调用。

## 补充观察

### 目录推送去重需要保留失败恢复路径

[src/App.tsx](../src/App.tsx) 第 115–118 行在请求成功前就记录 catalogSigRef。若首次推送失败，后续同内容会被签名直接拦下；syncCatalog 也没有将成功状态返回给调用方。

这是本轮性能改动中需要补的边界。建议把“正在发送”和“已成功发送”的签名分开，失败后允许重试，并测试首次失败、后续恢复时目录能自动到达服务端。本项来自代码路径核对，未进行真实断网端到端试验，单独列为补充观察。

### lint 警告不应通过恢复整个 db 依赖来消除

目录 effect 的去重修复有价值。直接把每次渲染变化的整个 db 对象放回依赖，会重新引入不必要的 effect 执行。可提取稳定的 syncCatalog 引用并作为依赖，同时保持成功后去重与失败重试的语义。
