## T1 · P1：基准版本升高后，再改题目仍可能复用同一有效版本

**位置**：[server/db.mjs](../server/db.mjs)，第 1333 行；[src/content/enrichments.ts](../src/content/enrichments.ts)，第 31–32 行。

服务端升版优先使用旧的 `prev.contentVersion`，只在缺失时才回退到基准版本。前端则取较大的基准版本来防止覆盖层降版。

这两条规则组合后会产生问题：基准版本已经很高，账户覆盖版本仍在较低值逐次增长，期间多次实质内容改变都会被前端显示为同一个基准版本。

### 实际复现

先按正常流程修改和撤回选项，使账户覆盖版本为 3；再把基准版本推到 10，随后改换错误选项：

```text
修改前有效选项：[yes, no]
修改前有效版本：10
修改后有效选项：[yes, maybe]
修改后覆盖版本：4
修改后有效版本：10
```

不同题面再次共用版本 10，学习证据中的版本等值判断无法区分修订前后的作答。前端“不向下覆盖版本”避免了降版，但没有保证内容变化一定得到新版本。

### 修复方向与验收

- 至少从旧覆盖版本和当前基准版本的最大值递增，而不是仅将基准作为缺省值。
- 更完整的方案是让有效修订明确包含基准修订与账户覆盖修订，并供审核、展示和作答统一使用。
- 验收必须包括：基准版本高于覆盖版本 → 改选项 → 有效版本变化 → 旧证据失效。
- 保留本轮已修好的相同内容不升版、撤回内容会升版行为。

## T2 · P2：切账户后维护不会重新启动，旧任务还可能接着补新账户

**位置**：[src/store/useDbSync.ts](../src/store/useDbSync.ts)，第 298 行、第 359–382 行；`enrichNow` 第 286 行；`switchTo` 第 544 行起。

`autoPipelineRef` 是整个 Hook 生命周期内的一个布尔值。A 启动过维护后它永久为 true，切到 B 没有重新建立 B 的维护状态。

与此同时，外层维护函数在 `await aiReviewNow()` 后不检查任务所属账户，接着调用 `enrichNow()`。后者从当前 accountRef 读取账户。因此，A 的审核因切换而中止客户端回写后，外层仍可能直接对 B 补纠正，而没有先为 B 执行审核。

### 真实 Hook 控制流验证

内存测试桩执行现有维护 effect 与 switchTo：

```text
场景一：A 完成维护后切换到有待办的 B
接口调用：[review:A]
当前账户：B
autoPipelineRef：true
B 没有启动 review

场景二：A 的 review 尚未返回时切到 B，再让 A 返回
接口调用：[review:A, enrich:B]
当前账户：B
autoPipelineRef：true
B 没有执行 review，却进入了 enrich
```

原来的 A 标记混进 B 已被修好，此处是维护任务生命周期的另一个边界，不是说原保护无效。

### 修复方向与验收

- 维护状态按 accountId 保存，或给每次维护绑定账户和代次。
- 整条流程固定账户身份，每个 await 后检查任务是否仍有效；不能到下一阶段重新读取当前账户来改变任务对象。
- 切换后旧任务停止后续阶段，新账户能独立启动自己的审核与补纠正。
- 验收覆盖 A 完成后切 B、A 正在审时切 B、A 正在补时切 B 三种时机。

## T3 · P2：返修桶内部仍固定取前 60 道，重复审核也继续被算作进展

**位置**：[server/db.mjs](../server/db.mjs)，第 1250–1264 行；[src/store/useDbSync.ts](../src/store/useDbSync.ts)，第 349 行。

新题优先确实解决了新题被饿死的问题。但 fix 桶内部仍保持 skill/id 固定顺序，没有轮转、最近处理时间或重试预算。

另外，客户端的停止条件仍是 `!res.reviewed && !res.rewritten`。即使重复改稿已经正确回报 unchanged，只要重复保存了审核结论，reviewed 仍大于零，客户端就继续下一轮。

### 实际复现

临时库中放入 61 道已经处于 fix 状态的题，模型稳定返回同一问题和同一份改稿。连续调用真实流水线路由六次：

| 轮次 | reviewed | rewritten | rewriteUnchanged | pending |
| --- | ---: | ---: | ---: | ---: |
| 1 | 60 | 60 | 0 | 61 |
| 2 | 60 | 0 | 60 | 61 |
| 3 | 60 | 0 | 60 | 61 |
| 4 | 60 | 0 | 60 | 61 |
| 5 | 60 | 0 | 60 | 61 |
| 6 | 60 | 0 | 60 | 61 |

第 61 道的审核记录完全未更新，也没有得到任何改稿。

### 修复方向与验收

- 保留新题优先，但 fix 桶按最近处理时间、公平轮转或可持久化的重试调度分配机会。
- 区分“调用过审核”与“状态或内容有推进”；同结论、同内容的重复结果不应继续消耗整轮预算。
- 设置单题重试上限与冷却，使一个难题不会占据每次开机的处理机会。
- 验收要使用超过单批上限的 fix 题集，不能只验证一条 fix 与一条新题的优先级。

## T4 · P2：目录推送失败后没有再次触发，成功后才记签名还不够

**位置**：[src/App.tsx](../src/App.tsx)，第 108–125 行；[src/store/useDbSync.ts](../src/store/useDbSync.ts)，`syncCatalog`。

当前实现正确地只在成功时更新 catalogSigRef。但失败后仅返回 false，没有安排定时重试、在线事件重试或重试状态更新。

effect 依赖是 `[accountPool, syncCatalog]`。目录不变、两个引用不变时，普通重渲染不会再次执行 effect。让签名保持为空只是允许下一次调用发送，并不会产生下一次调用。

### 触发条件与影响

- 初始目录请求在服务启动、重启或短暂网络异常时失败。
- 此后题目内容及账户题池引用没有变化。
- 当前会话内没有主动重试，服务端仍保留空目录或旧目录，自动维护就可能缺题或不启动。

此项为代码路径核对，未宣称做了真实网络故障的浏览器端到端复现。

### 修复方向与验收

- 增加有限退避重试或在线恢复事件，并区分正在发送、已成功送达和待重试的签名。
- 处理组件卸载与请求重叠，避免修复失败恢复后重新引入重复全量推送。
- 验收：首次返回失败，之后接口恢复；不切账户、不改变题库、不刷新页面，也能完成同步。

## T5 · P2：skip-checks 发布包可能是旧前端加未提交后端，却标成 HEAD 版本

**位置**：[scripts/release.mjs](../scripts/release.mjs)，第 26–39 行、第 50–55 行、第 80 行及第 112 行。

`--skip-checks` 不只跳过测试，也跳过了 dist 构建，并允许脏工作区继续打包。随后脚本直接从工作目录复制 server 和 dist，再把 VERSION 写成 HEAD 短哈希。

这与警告中的“未提交的改动不会进包”相反，也与最终固定输出的“dist 现场构建 ✓”不一致。部署健康检查只能看到写入的 VERSION，无法识别这个混合版本。

### 临时 Git 仓库复现

用实际 release 脚本，准备已提交的后端、已有旧 dist，再修改后端但不提交，执行 `--skip-checks`：

```text
VERSION = 临时仓库 HEAD
发布包 server/api.mjs = UNCOMMITTED-backend
发布包 dist/index.html = stale-frontend
脚本仍输出：dist 现场构建 ✓
```

没有运行真实项目发布或部署。

### 修复方向与验收

- 将“跳过测试”与“跳过构建”分开；发布构建应始终来自明确的源码状态。
- 如仍用 HEAD 作为正式版本，应拒绝脏工作区，或从该提交的隔离快照取全部源文件并构建。
- 如允许开发快照发布，应使用能区分脏内容的独立版本标识，明确标注构建来源与校验状态。
- 日志按实际执行情况输出，不在跳过构建后声称现场构建成功。
- 验收覆盖干净正常发布、脏工作区、跳过测试、已有过期 dist 四种组合。

## 需要保留的产品取舍说明

本轮将缺错因标签改成 `tagGaps` 提示，不阻塞纠正完成。这是明确写进实现的取舍，与此前“缺标签也自动补齐”的建议不同。

本次不把它重复列为一个未解释的代码缺陷。但后续对外状态应区分“错误选项纠正完整”和“错因标签完整”。若下一步做错因驱动补练，仍需要一个有预算限制的标签补全流程，或明确采用其它可用的错因来源。

## 下一步建议

1. 先修 T1，确保任何实质题面变化都产生不同的有效修订，避免学习证据混用。
2. 将维护任务的账户身份固定下来，再完成 T2/T3/T4 的生命周期、公平调度和失败恢复。
3. 发布前处理 T5，保证版本断言对应真实构建内容，而不只是 VERSION 文件的字符串。
4. 将本次边界加入自动化回归；现有纯函数与数据层测试应继续保留，同时补维护流程级测试。

建议下一轮按三条不变量验收：

- 相同有效版本必须对应相同的题意与判分内容。
- 一次维护任务从开始到结束始终属于同一账户。
- 处理失败和无变化结果不能永久阻塞其它待办，也不能依赖用户刷新页面才能恢复。
